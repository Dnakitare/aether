# Aether v1.0 Scope

**Status:** Draft — proposal for scope cut
**Date:** 2026-04-27
**Owner:** @dnakitare

## Premise

The current README roadmap (Q3 2026) lists multi-region support, full CRIU-based
VM checkpoint/restore, 80%+ test coverage, security audit, and performance
benchmarks as v1.0 gates. None of those have been started, and two of them
(CRIU, multi-region) are roadmap theater — they require sustained, focused work
that the past ten weeks of activity (module rename, OSS hygiene, infrastructure
codification, bug-fix sweep) have not produced.

There is also an internal contradiction between the README's coverage target
(line 491: ~35% today, 60% for v1.0) and the roadmap (line 401: 80%+). One of
those needs to win. This document picks one.

This document re-baselines v1.0 to what is actually built and can be hardened
in the time available, and explicitly defers the rest. The goal is a v1.0 that
ships, not one that slips.

## What v1.0 is

A **single-region, hardware-isolated agent runtime** with the integrated
control plane that already exists today: HTTP API, JWT/RBAC auth, in-process
scheduler, PostgreSQL state, Redis quotas, OpenTelemetry observability, and
Helm/Terraform deployment for AWS.

v1.0 ships when, and only when, this surface is hardened to the criteria
below — not when feature parity with the original Phase-6 vision is reached.

## In scope for v1.0

- [ ] Hardened core path: API → scheduler → Firecracker VM → state → metrics
- [ ] Auth: JWT (HS256 and RS256), API keys, RBAC, per-tenant isolation
- [ ] In-process scheduler (single-region)
- [ ] PostgreSQL state with migrations CLI
- [ ] Redis-backed tenant quotas
- [ ] Observability stack (Jaeger, Prometheus, Grafana, Loki)
- [ ] Single-cloud deployment (AWS) via Helm + Terraform
- [ ] Metadata-level checkpoint save/restore (current implementation)
- [ ] Operational runbooks for the in-scope surface

## Out of scope for v1.0 (deferred)

Each of these is deferred with a target. They are not abandoned — they are
acknowledged as larger than the time remaining.

| Feature | Status | Defer to | Why |
|---|---|---|---|
| Full CRIU VM checkpoint/restore | Not started | v1.1 | Requires CRIU integration spike + correctness testing; metadata-only is sufficient for v1.0 use cases |
| Multi-region support | Not started | v2.0 | Requires control-plane redesign for cross-region state; out of reach in 5 months |
| Azure deployment | Not started | v1.1+ | No adapter exists; deferred until there's demand |
| GPU support | Not started | Q3 2026 (post-v1.0) | Already on roadmap as post-v1.0 |
| Edge deployment | Not started | Q4 2026 (post-v1.0) | Already on roadmap as post-v1.0 |
| 1,000+ agent load testing | Not started | v1.0 (gate) → see criteria below | Required for v1.0 claim, but moved to a measurable gate |

## Experimental surface in v1.0

The component below stays in the repo and on `main`, and users can opt in,
but it is **not part of the supported v1.0 surface**. It is explicitly
excluded from the coverage denominator (criterion #1), the external security
review (criterion #2), and the 1,000-agent load test (criterion #3). It
will be labeled `experimental` in code comments, README, and CHANGELOG.

- **GCE node provisioning** (0% coverage today) — EC2 is the only supported
  provisioner for v1.0

The Kafka messaging and HashiCorp Vault paths that were previously listed
here have been removed in the single-region refactor (see CHANGELOG). Aether
is single-region with an in-process scheduler; env vars and Kubernetes
secrets are the supported secret sources, and there is no Kafka, etcd, or
Vault dependency.

Promotion path: an experimental component is promoted to supported in a
later minor release once it meets the same gates v1.0 itself meets (coverage,
security review pass, load-test inclusion).

## Shipping criteria (the four things that gate v1.0)

These replace the current roadmap's bullet list. Each is measurable.

1. **Test coverage ≥ 70% on the in-scope surface.** Not 80% globally — 70% on
   the path that ships. Experimental packages (GCE — see
   "Experimental surface in v1.0" above) and deferred packages (Azure, GCP
   beyond GCE, multi-region) excluded from the denominator. Coverage files in
   the repo root regenerated by CI on every merge — the current pattern of
   stale `coverage*.out` files at root committed in mid-February stops.
2. **One external security review pass.** Not a full audit — one pass by a
   reviewer outside the project, focused on the auth, multi-tenant isolation,
   and Firecracker boundary surface. Findings triaged; P0/P1 closed before
   ship.
3. **Load test at 1,000 concurrent agents on a single AWS region.** Recorded
   p99 latency, scheduler throughput, and failure modes. Published as
   `docs/V1_LOAD_TEST.md` with the raw numbers, not summary claims.
4. **One real adopter running v1.0-rc on a non-toy workload for ≥ 2 weeks.**
   Doesn't need to be in production. Needs to be someone other than the
   author, exercising the API, hitting bugs, and reporting them. Without
   this, "v1.0" is a self-graded label.

## Non-goals

- Catching up to the README's current claims. The README will be edited to
  match this scope before v1.0 ships, not the other way around.
- Hitting Q3 2026 if the criteria above aren't met. Slipping the date is
  cheaper than shipping a v1.0 that's still really beta.

## Risks

- **Adopter risk (criterion 4).** Solo project, no existing user base. May
  need to seed this — a friendly user, a CTF infrastructure team, a code-
  execution sandbox project. If no adopter materializes by 2026-07-01, the
  criterion needs revisiting (drop to "internal load run + bug-bash week"?).
- **Security review cost.** External reviewers cost money or favors. Budget
  needs deciding before this document is final.
- **Coverage gaming.** "70% on the in-scope surface" is gameable by writing
  shallow tests. The intent is real test depth on the auth and isolation
  paths; CI should track branch coverage, not just line coverage, on those
  packages specifically.

## Tracking

- README roadmap section will be rewritten to match this document once
  approved.
- CHANGELOG `[Unreleased]` section will be replaced with a v1.0 work-item
  list derived from the in-scope checklist above.
- Per-criterion progress tracked in GitHub issues labeled `v1.0-gate`.
